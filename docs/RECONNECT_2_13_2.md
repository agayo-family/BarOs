# BarOS 2.13.2: частое появление экрана восстановления

2 ноября 2026 года. Исправление продолжается от опубликованной 2.13.1; данные, тарифы, вход, курсы и Tincture Lab не переносились и не изменялись.

## Подтверждённые факты

- Рабочий сервис `baros-staging` остаётся на Render Free во Франкфурте. Он не приостановлен, последняя 2.13.1 опубликована успешно.
- В журнале за 14:00–18:30 UTC есть штатные остановки и новые запуски, в том числе остановка в 16:51:52 UTC и запуск в 18:26:39 UTC. Событий `server_failed` и ошибок уровня error за запрошенный период не найдено. Потребление памяти в полученных пятиминутных измерениях — около 134–193 млн байт при лимите около 537 млн; нехватка памяти этой выборкой не подтверждается.
- Render официально останавливает бесплатный веб-сервис после 15 минут без входящего трафика; запуск по следующему запросу занимает примерно минуту: https://render.com/docs/free. Это объясняет ожидание после простоя. Журнал не позволяет приписать каждый увиденный пользователем случай только этой причине.
- Старый service worker немедленно превращал единственный сетевой сбой или любой HTTP 5xx в экран «Не удаётся открыть BarOS» с полной перезагрузкой каждые восемь секунд. Он не отличал короткий сбой от более длительной недоступности.
- В браузере `/health` ответил `status=ok`, `service=baros`, `version=2.13.1` до публикации исправления.

## Исправление

1. Только навигационные GET повторяются после сетевого сбоя или 502/503/504: максимум две дополнительные попытки, задержки 400 и 1200 мс. HTTP 500 не умножается. При известном браузеру отсутствии сети лишних попыток нет. Исходный Request и адрес сохраняются; API, POST и `/health` не перехватываются и не повторяются.
2. Вместо немедленного объявления ошибки появляется понятное состояние подключения. После длительного ожидания текст честно сообщает, что сайт пока не отвечает. Есть ручная проверка, светлая/тёмная тема, клавиатурный фокус и уменьшение анимации.
3. Восстановление проверяет готовность приложения и БД через `/health`, затем настоящий HTML по исходному адресу. Ответ 200 от страницы запуска хостинга не считается успехом. Работающий `/health` при ошибке самой страницы не запускает цикл перезагрузок. После подтверждения выполняется один reload исходного адреса с его query и hash.
4. Скрипт восстановления заранее сохраняется как общедоступный статический ресурс и доступен даже при недоступном сервере. HTML, проверка готовности, личные API и данные сотрудников не кэшируются. Добавлена ограничивающая CSP для аварийного документа.
5. Между проверками используется задержка до 30 секунд; в скрытой вкладке запросы приостанавливаются. Автоматические проверки прекращаются через три минуты, ручная кнопка запускает новый ограниченный цикл. Повторные нажатия не создают параллельные запросы. Без JavaScript остаётся обычная ссылка и запасное обновление раз в 30 секунд.

Это исправление устраняет лишние экраны при коротком сбое и цикл обновлений, но не отменяет сон бесплатного хостинга. Для постоянной доступности нужен постоянно работающий сервис; платные услуги и реквизиты хостинга в этом выпуске не подключались.

## Проверки

Локальный `node tests/service_worker_audit.mjs` проходит: временные 502/503/504, сетевая ошибка, устойчивый 500, настоящее отсутствие сети, точное сохранение Request, обход API/записи/health, доступность скрипта без сети, распознавание реального HTML и готовности, ошибочный ответ 200 от хостинга, работоспособный health при неисправной странице, отсутствие параллельных проб, пауза в скрытой вкладке, остановка после ухода, лимит автоматических попыток и ручное возобновление.

В оба существующих прохода Chromium добавлена проверка реального service worker: единичный 502 устраняется незаметно, после полного отключения сети восстановление открывает тот же адрес автоматически. Итоги CI и публикации добавляются только после фактического завершения.
